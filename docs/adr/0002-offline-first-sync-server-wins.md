# Offline-first sync with server-wins conflict handling

Technicians work in places with poor connectivity, so every create, edit and delete is saved to the local Room database first and synced later by a background worker with retry and backoff. Room is the single source of truth for the UI. Incidents and photos each carry their own Sync State.

When a queued change reaches the server after an Operator has moved the Incident out of `OPEN`, the server rejects it with `409 Conflict`. The client marks the change `Failed` with the reason "already being handled", discards the local edit, and shows the server's version.

Incident IDs are generated by the client as UUIDs, and `POST /incidents` is idempotent by ID, so retries never create duplicates.

## Considered options

- **Online-only:** far simpler, but a Technician in a dead zone cannot report anything.
- **Last write wins:** simple, but overrides an Operator who is already acting on the Incident.
- **Let the Technician resolve conflicts, or use a version field:** more general, but adds UI and contract complexity to three clients.
- **Offline-first with server wins (chosen):** protects the Operator's work with the simplest possible rule.

## Consequences

- A Technician's discarded edit is lost unless they copy it from the failed-sync message, which is an accepted trade-off.
- The contract needs a `409` response and client-generated IDs, and all three clients depend on both.
- The pending-change queue and Sync State machine become the most important logic to test.
